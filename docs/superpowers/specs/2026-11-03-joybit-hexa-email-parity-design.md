# Joybit 邮箱账号流程与 Hexa Landing 对齐

## 意图与边界

用户决定完整复用 Hexa Landing 的邮箱账号流程，同时保留 Joybit 的 React Native 界面与七语言支持。两个 App 已共用同一个 Supabase 项目和用户身份；已在 Hexa 确认邮箱的玩家应能用原邮箱和密码登录 Joybit，无需迁移账号或再次注册。Joybit 内进入 Hexa Landing 时仍传入 Joybit 会话，不显示游戏自己的登录页。两个独立 App 的本机会话不自动共享。

本轮“完整邮箱流程”包括：邮箱密码登录、注册与密码确认、注册邮件验证码、未确认账号续办、重发验证码及倒计时、忘记密码邮件验证码、新密码确认，以及这些步骤中的输入校验和明确的错误提示。首版仍仅向 Joybit 用户展示邮箱入口；Hexa 独立 App 的 Apple 登录和独立界面不引入 Joybit。Joybit 品牌和七语言范围保持不变。账号删除继续使用现有 Joybit 流程。

## 现状与差距

Hexa Swift 客户端的 `AuthModel`/`AuthService` 已实现以上流程；它要求邮箱有效且不超过 254 字符，注册密码至少 8 个字符且 UTF-8 不超过 128 字节，邮件验证码是 6–10 位 ASCII 数字。注册完成或重发成功后等待 60 秒；未确认账号密码登录遇到 `email_not_confirmed` 会进入验证码页。它还提供返回登录和更改邮箱入口，验证完成前清除表单中的密码，并有邮件验证码找回密码。

Joybit 当前 React Native 客户端已通过 Supabase JS 实现密码登录、注册、注册码验证和重发，但没有确认密码、输入校验、重发倒计时、未确认账号续办和找回密码页。Joybit 当前把整个邮箱转成小写，Hexa 只清理空白并把域名转小写；对齐时沿用 Hexa 的规则，避免改变邮箱本地部分。

## 方案

**已选：在 Joybit 现有七语言界面中补齐 Hexa 的完整邮箱行为，共用同一 Supabase 后端。** 保留 Joybit 的 React Native 登录页，使其以后可用于 Android。将邮箱规范化、校验和验证码倒计时做成可测试的独立逻辑；在 `AuthProvider` 中使用现有 Supabase 客户端调用登录、注册、验证、重发和恢复接口。Swift 版仍由独立 Hexa App 维护，Joybit 不复制 Swift 登录视图。

比较过的其他方案：直接嵌入 Hexa Swift 登录页可最大程度复用 iOS 页面，却会显示 Apple 入口、只有英日韩、Android 无法共用，且需要把 Swift 登录会话再传回 Joybit；只复用 Supabase 后台已是现状，不能补足玩家缺失的邮箱操作。

## 玩家流程

1. **已有账号登录：** 玩家输入 Hexa 的邮箱和密码，Joybit 使用相同项目验证；成功后回到之前点选的游戏或账号页。错误密码、未验证邮箱、限流和离线状态给出对应语言提示。已经确认的邮箱不会再次收到注册码。
2. **注册：** 邮箱、密码和确认密码先在本地校验。请求成功且服务器未返回会话时进入注册验证码页，显示不可编辑的待验证邮箱，并清除密码字段。服务器可能出于防止枚举隐藏已有账户，因此提示只说明“如果可以发送，请检查邮箱；已注册则返回登录”，不保证实际发信。
3. **未确认账号续办：** 密码登录收到 `email_not_confirmed` 时直接进入同一验证码页，可重发注册码；重启后也能重新登录进入该页。取消或更换邮箱时清除本次输入，不删除服务器账号。
4. **验证码与重发：** 只接受 6–10 位 ASCII 数字；无效或过期则停留在当前页面。注册请求或成功重发后本地 60 秒倒计时，重发按钮禁用；服务端限流仍为最终约束。退出页面时不保留明文验证码。
5. **找回密码：** 登录页可请求邮件恢复码。显示中性反馈，避免暴露邮箱是否存在。输入恢复码、新密码和确认密码；先用一个不持久化的临时 Supabase 客户端验证 `recovery` 码并更新密码，全部成功后才把新会话交给 Joybit 主客户端。失败或中断不应让 Joybit 误以为已登录。恢复邮件模板需含 `{{ .Token }}`；若共享项目模板尚未配置，先核对并准备不会破坏 Hexa 的修改。

## 共用后端与安全

- Joybit 与 Hexa 使用同一 Supabase 项目。阿里云邮件服务若已作为该项目的 SMTP 发信端，就由两款 App 共用；它负责送信，账号、验证码校验和会话仍由 Supabase Auth 负责。
- 不新增 Supabase 项目或独立用户表。确认邮件、恢复邮件的模板和 SMTP 配置属于共享项目，变更会同时影响 Hexa。先只读核对配置；需要改动时，先准备确切变更和影响，再进行外部配置操作。
- 密码和验证码仅保留在当前表单内存，发送后清理；不写入日志、AsyncStorage 或 WebView。正式会话沿用 Joybit 的 SecureStore。Joybit 的原生 Hexa 视图仍只接收进入游戏所需的现有会话。
- 未验证、过期或无效的验证码不能进入游戏；已退出登录的玩家不能用离线小游戏绕过登录门槛。恢复码验证后的临时会话不可在密码更新失败时提升为 Joybit 主会话。

## 七语言与体验

所有新增邮箱流程、错误和读屏标签沿用 Joybit 的英语、日语、韩语、法语、西班牙语、俄语、德语；设置中的语言切换继续生效。输入框使用邮箱与一次性验证码键盘类型，长文案可滚动，小屏幕和软键盘下仍能操作。不会让 Hexa 的英日韩 Swift 登录页出现在 Joybit。

## 验收与限制

自动测试覆盖注册/登录/续办/重发/找回密码的状态转换、边界输入、错误映射、60 秒倒计时、临时恢复会话隔离、七语言文案和此前的离线会话行为；现有 Hexa 回归测试、TypeScript 检查与 iOS 构建通过。使用已确认的 Hexa 账号验证 Joybit 登录，且不要求玩家重新注册；验证码邮件及重置邮件的真实送达须在共享 Supabase 项目发信配置就绪后，用测试邮箱端到端检查。签名版设备上的 Keychain 和游戏内会话传递仍以实际构建验证为准。
