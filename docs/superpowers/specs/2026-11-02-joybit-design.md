# Joybit 首版设计（已确认）

## 目标与范围

Joybit 是先在 iOS 推出的小游戏集合，后续支持 Android。打开应用直接进入游戏目录；首版兼容原生和 H5 游戏，并以 disclick 仓库中的 Hexa Landing / Steady Drop 作为首款游戏。

反目标：打开 Joybit 就被游戏登录页挡住；将示例人数显示为真实人数；让用户以为离开 Joybit 的独立 App 是平台内游戏。

## 已决定的方案

- 平台外壳采用 React Native，共用 iOS 与将来的 Android 界面。原生游戏分别提供各平台实现，H5 游戏在应用内网页视图运行。
- 首页采用双列、可纵向滚动的游戏卡片。每张卡片显示主图、名称、玩过人数与收藏按钮。
- 人数少于 1000 时显示准确数字；达到 1000 后使用向下取整的整数和单位（如 1千、2万），避免夸大人数。真实人数由后端提供，缺失时不显示虚构数据。
- 左上角菜单按钮打开左侧抽屉，含用户信息、收藏、设置入口。抽屉打开时底部固定广告位收起；关闭后恢复。
- 收藏列表与首页使用同一游戏目录数据。未登录时收藏暂存在本机；登录后合并到 Joybit 账号并随账号同步。

## 统一账号（用户新增要求）

- Joybit 启动后仍直接显示游戏列表；用户可在左侧“用户信息”入口登录，也可在第一次进入需要登录的游戏时登录。
- Joybit 与 disClick 使用同一个 Supabase 项目和用户身份，复用 disClick 已有的邮箱密码和 Apple 登录方式，让现有账号可继续使用。
- Joybit 负责一次登录和安全保存会话。进入 disClick 原生游戏时传递同一会话；游戏不再弹出第二套登录页。退出账号后游戏与平台同时退出。
- disClick 原有生命值账本继续关联同一用户。其关卡进度目前按账户保存在本机；统一账号本身不改变这一点，跨设备进度同步另行设计。
- Joybit 使用自己的 iOS 应用标识和 Apple 登录配置；原游戏的签名和商店配置不能直接复用。首页广告与游戏内激励广告共享同一隐私选择，但分别使用适用于 Joybit 的广告位配置。
- disClick 独立 App 继续维护。游戏核心只维护一份，由独立 App 与 Joybit 的 iOS 原生模块共同引用；两个 App 可以各自发布版本。
- 用户已决定首版不迁移独立 App 的本机关卡进度。现有用户在 Joybit 内的关卡进度将从头开始，两个 App 的本地进度彼此独立；生命值仍使用同一账号的服务器账本。

## 首款游戏调查结果

disclick 私有仓库的 `main` 分支是 SwiftUI + SpriteKit iOS 游戏。它已有独立登录、Supabase 生命系统、关卡进度与激励广告；仓库 README 记录曾以 Hexa Landing 名称提交独立 App 审核。该游戏不是可直接放入 WebView 的 H5 游戏。

**用户已确定在 Joybit 内直接玩。** 实现时把 SwiftUI 游戏界面及 SpriteKit 场景封装为 React Native 可呈现的 iOS 原生视图；从游戏返回 Joybit 首页。Joybit 与游戏共用同一个账号和会话，保留游戏现有的 Supabase 生命系统。现有独立 App 的签名、广告配置和商店资料不能直接视为 Joybit 的配置。

## 比较过的方式

1. **React Native 共用平台外壳（已选择）**：目录与菜单可跨平台复用；原生游戏需按 iOS/Android 分别接入。
2. **SwiftUI iOS 外壳**：接入现有游戏较直接，但 Android 版需要重建平台界面。

对于 disclick 的入口，用户选择在 Joybit 内直接玩。另一种跳转其独立 App 的方式接入较快，但用户会离开 Joybit，因此未采用。

## 首版不包含

- 在未提供数据源前展示真实游玩人数或在线广告。
- 未提供的其他游戏的实际接入。
- Android 发行包；工程保留跨平台结构。

## 实施时由构建者确定

- 共享游戏核心的具体代码组织方式；需要保证两个 App 都可以构建和发布。
- 首页主图的制作方式；未提供游玩人数和广告平台配置前，保留清晰的空状态或测试占位，不发布虚构数据或真实广告。
